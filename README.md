# jario (자리)

> 창업할 자리를 고를 때, 반경 500m 안에 같은 업종이 몇 개인지부터 본다.

**https://jario-pysoya1.vercel.app**

[![ci](https://github.com/PYSoYa/jario/actions/workflows/ci.yml/badge.svg)](https://github.com/PYSoYa/jario/actions/workflows/ci.yml)

지도에서 위치를 찍으면 그 주변의 경쟁 밀도·업종 분포를 계산해주는 상권 분석 서비스.
소상공인시장진흥공단이 공개하는 전국 상가업소 데이터를 기반으로 한다. 현재 **서울·인천** 691,087곳을 담고 있다.

## 무엇을 볼 수 있나

지도에서 자리를 찍거나 장소를 검색하면 세 가지를 답한다.

**이 자리는 어떤가** — 반경 안 업소 수와 업종 구성. 같은 도구로 상권의 성격이 갈린다.

```
부평역 500m   3,074곳   여성 의류 188 · 백반/한정식 171 · 네일숍 125 · 카페 112
강남역 500m   6,615곳   경영 컨설팅 866 · 광고 대행 438 · 부동산 중개 376
홍대입구역     5,145곳   펜션 344 · 카페 292 · 경영 컨설팅 205
```

**어느 동네가 나은가** — 행정동별 입지계수(LQ). 업소 수를 그냥 비교하면 큰 동네가 항상 이기므로
상권 규모로 나눠서 본다. 카페 기준 상위는 개항동 2.83(개항장 카페거리), 안암동 2.63(고려대 앞).

**A와 B 중 어디인가** — 후보지 두 곳을 나란히 놓은 비교 리포트. 로그인 없이 링크로 공유한다.

## 데이터 실사 (인천 첫 적재 기록)

스키마를 짜기 전에 원본을 먼저 확인했다. 결과는 예상보다 깨끗했다.

| 항목 | 결과 |
|---|---|
| 행 수 | 136,995 |
| 컬럼 | 39개 (UTF-8) |
| 상가업소번호 중복 | 0 → 자연키를 PK로 사용 |
| 좌표 결측·파싱 실패 | 0.00% |
| 컬럼 수 불일치 행 | 0 |
| 업종 코드 계층 일관성 | 100% (`G2` → `G204` → `G20404` 접두어 구조) |
| 코드→명 매핑 | 업종·지역 전부 1:1 |
| 행정동 | 158개 / 시군구 11개 |

확인해서 건진 것들:

- **동봉된 안내문이 틀렸다.** `[필독]파일열람방법.txt`는 업종 대분류를 8개(관광/여가/오락, 부동산, 생활서비스, …)라고 적어놨지만 실제 데이터는 **10개이고 분류 체계 자체가 다르다**(음식, 소매, 수리·개인, 과학·기술, 교육, 예술·스포츠, 시설관리·임대, 부동산, 보건의료, 숙박). 문서 대신 데이터를 봤다.
- **`호정보`·`동정보`는 100% 빈값**이라 컬럼을 아예 만들지 않았다.
- **`층정보`에 층이 아닌 값이 섞여 있다.** `1103`, `2302`, `15015` 같은 값은 층수가 아니라 호실번호(11층 3호)다. 범위 가드(-10~200)로 걸러 34건을 `floor_no`에서 제외하고 `floor_raw`에 원문을 보존했다. `지`(823건) → -1, `B1`~`B3` → 음수 층으로 정규화했다.
- 시군구에 **제물포구·영종구·서해구·검단구**가 있다. 2026년 인천 행정구역 개편이 반영된 데이터다.

서울을 더할 때 한 가지가 더 나왔다. **`B17`·`B26`·`B40`** — 국내 최심도는 B7~B8 수준이라
지하 40층은 존재하지 않는다. 호실번호다. 숫자 층에만 범위 가드를 걸고 지하 표기는 두 자리까지
무조건 받고 있었는데, `CHECK` 제약이 그걸 잡았다. 인천만으로는 드러나지 않던 케이스다.

재현: `pnpm data:inspect data/<파일>.csv`

성능은 [응답 68초를 0.2초로](#응답-68초를-02초로)에 따로 정리했다.
`pnpm db:check` 로 좌표계와 인덱스 사용을 검증한다.

## 왜 데이터를 우리 DB에 적재하는가

공공데이터포털은 반경 조회 API도 함께 제공한다. 그런데도 CSV를 받아 적재하는 쪽을 택했다.

- 이 서비스의 본체는 조회가 아니라 **집계**다. "반경 내 동종 업소 수", "업종별 밀집도", "과밀 지역 탐색"은 남의 API 응답을 모아서는 만들 수 없다.
- 지도를 팬/줌할 때마다 외부 API를 때리면 호출량 제한에 바로 걸린다.
- 해당 데이터의 이용허락범위가 "제한 없음"이라 적재에 제약이 없다.

그래서 PostGIS가 선택이 아니라 전제가 된다.

## 거리 계산: 좌표계를 먼저 정한 이유

원본 좌표는 WGS84(EPSG:4326)다. 여기서 `ST_Distance`를 그냥 부르면 결과 단위가 **미터가 아니라 도(degree)**다.
도를 미터로 바꾸려고 상수(111,320)를 곱하는 코드를 흔히 보는데, 그게 왜 틀리는지 인천 좌표로 확인했다.

인천시청(126.7052, 37.4563)에서 **같은 0.005°만큼** 떨어진 두 점의 실제 거리:

| 방향 | `geography` | EPSG:5179 | 도 × 111,320 |
|---|---:|---:|---:|
| 동쪽 0.005° | 442.4 m | 442.2 m | 556.6 m |
| 북쪽 0.005° | 554.9 m | 554.7 m | 556.6 m |

경도 1도의 실제 거리는 `cos(위도)`에 비례해 줄어든다. 그래서 위도 37.46°에서 동서 방향은 남북 방향의 약 80%다.
상수 곱셈은 **동서 방향을 114m(26%) 과대평가**한다 — 반경 500m가 핵심 기능인 서비스에서는 결과가 통째로 틀어지는 크기다.

`geography` 타입과 EPSG:5179 투영은 0.2m(0.05%) 차이로 둘 다 정확하다.
**`geography`를 채택**했다 — 매 쿼리마다 `ST_Transform`을 부르지 않아도 되고, GiST 인덱스가 그대로 동작한다.

재현:

```bash
pnpm db:up
pnpm db:migrate
pnpm db:check
```

## API

### `GET /api/places/nearby`

| 파라미터 | 필수 | 범위 | 기본값 |
|---|---|---|---|
| `lon` | ✓ | 124 ~ 132 | — |
| `lat` | ✓ | 33 ~ 39 | — |
| `radius` | | 50 ~ 2000 (m) | 500 |
| `industry` | | 업종 코드 (2·4·6자) | 전체 |
| `limit` | | 1 ~ 2000 | 500 |
| `order` | | `distance` \| `sample` | `distance` |
| `group` | | `sub` \| `top` | `sub` |

### `GET /api/spot?lon=&lat=&radius=&industry=`

화면이 실제로 쓰는 엔드포인트. 업종 목록·분포·목록·마커를 한 번에 준다.
`nearby` 는 검증과 keepalive 용으로 남겨뒀다.

`GET /api/places/:id` 는 업소 한 건의 상세(지번주소·표준산업분류·행정동 등)를 준다.
목록 응답에 이 필드를 다 싣지 않는 이유는 목록이 최대 2,000건까지 나가기 때문이다.

### `GET /api/analysis/dong?industry=I21201`

행정동별 **입지계수(LQ)** — 그 동의 업종 비율 ÷ 서울·인천 전체의 업종 비율.
1보다 크면 상권 규모에 비해 그 업종이 몰려 있다.

업소 수를 그냥 비교하면 큰 동네가 항상 이긴다. 규모로 나눠야 "이 동네는 카페 동네인가"를
말할 수 있다. 카페(I21201) 기준 상위는 개항동 2.83(개항장 카페거리), 안암동 2.63(고려대 앞),
강화 길상면(관광지) — 실제와 맞는다.

두 가지를 조심했다:

- **표본이 작은 동을 걸러낸다**(`minTotal`, 기본 300). 업소 20곳인 섬에서 카페 2곳이면
  LQ가 2를 넘는다. 우연히 나온 숫자가 "카페 성지"로 읽힌다.
- **동의 대표 지점은 평균 좌표가 아니다.** 평균으로 잡으면 넓게 흩어진 동에서 그 점이
  정작 해당 업종이 없는 곳에 떨어진다 — 개항동은 반경 500m에 카페 1곳, 강화 길상면은
  0곳이었다. "카페가 가장 몰린 동네"라고 안내하면서. 약 450m 격자로 묶고 3×3 이웃을
  합쳐 가장 빽빽한 지점을 쓴다(개항동 1 → 63곳, 길상면 0 → 18곳).
  칸 하나만 보면 안 되는 이유는 칸(450m)이 반경(500m)보다 작아서, 인접한 두 밀집 칸
  사이의 지점이 어느 한 칸의 중심보다 나을 수 있기 때문이다(송도4동에서 실제로 그랬다).

**이 지표로 할 수 없는 말**: 낮은 LQ는 기회가 아니다. 업소 구성만 볼 뿐 인구·유동인구·
임대료·소득이 들어 있지 않아서, 적은 이유가 수요가 없어서일 수 있다. 화면에도 그렇게 적었다.

```bash
curl "http://localhost:3001/api/places/nearby?lon=126.7244&lat=37.4894&radius=500&industry=I2"
```

```jsonc
{
  "center": { "lon": 126.7244, "lat": 37.4894 },
  "radius": 500,
  "total": 3074,           // LIMIT과 무관한 실제 개수
  "truncated": true,       // items가 잘렸는지
  "breakdown": [ { "code": "G20902", "name": "여성 의류 소매업", "count": 188 }, … ],
  "items": [ { "name": "…", "industryName": "노래방", "distanceM": 66, … } ]
}
```

설계 노트:

- **총 개수를 목록과 따로 센다.** `items`에는 지도 마커용 상한이 걸려 있어서 `items.length`로는 밀집도를 알 수 없다. "이 자리 반경 500m에 몇 개"가 이 서비스의 답이므로 잘리지 않은 수가 따로 필요하다.
- **업종 필터는 접두어 매칭 하나로 3단계를 모두 받는다.** 코드가 대(2자) → 중(4자) → 소(6자) 접두어 구조이고 레벨별 길이가 균일함을 데이터에서 확인했다. 덕분에 레벨별 파라미터를 나누거나 조인을 늘리지 않아도 된다.
- **좌표 범위를 DB `CHECK`와 같은 값으로 API에서도 막는다.** 한국 밖 좌표는 좌표계를 잘못 쓴 것이지 사용자 입력이 아니다.
- **지도 마커는 `order=sample`로 뽑는다.** 가까운 순으로 자르면 밀집 지역에서 지도가 거짓말을 한다 — 부평역 반경 500m에서 가까운 순 500개는 전부 **120m 안**에 있어서, 바깥 380m가 업소 없는 땅처럼 보였다. `hashtext(place_id)` 순으로 뽑으면 위치와 무관하게 고르게 추려지고(중앙값 94m → 305m), 같은 입력에는 같은 표본이 나와 지도가 깜빡이지 않는다.
- `radius` 상한 2,000m — 없으면 요청 한 번으로 도시 전체를 긁을 수 있고, 도보권을 넘으면 상권 분석의 의미도 옅어진다.

## 후보지 A/B 비교 리포트

자리 두 곳을 골라 같은 업종·반경으로 나란히 본다. 저장하면 `/r/<id>` 링크가 나오고,
로그인 없이 그 링크로 공유한다.

```
                        부평구 동수북로    부평구 장제로
반경 안 전체 업소            3,074           1,147
카페 수                        112              47
가장 가까운 카페               70m             45m
행정동                 부평6동 LQ 1.18   부평5동 LQ 0.83
```

설계 결정 셋:

- **계산 결과가 아니라 입력만 저장한다.** 분기 스냅샷이라 같은 입력이면 같은 결과가 나오고,
  그래야 표가 커지지 않는다. 대신 어느 분기 데이터로 만든 리포트인지 남겨서, 다음 분기
  데이터로 바뀌면 "공유한 시점과 다를 수 있다"고 화면에 알린다.
- **id는 순번이 아니라 난수다**(12자 base64url ≈ 72비트). 로그인이 없으므로 추측 불가능성이
  유일한 보호막이다. 순번이면 남의 리포트를 훑어볼 수 있다.
- **행정동은 근사다.** 경계 폴리곤이 없어 가장 가까운 업소의 동으로 판단한다. 경계 근처에서는
  틀릴 수 있고, 그 사실을 리포트에 적었다.
- **시간당 20개까지만 만들 수 있다.** 로그인이 없어서 누구나 무제한으로 부를 수 있었고,
  스크립트 한 번이면 무료 티어 DB가 리포트로 찬다. 서버리스라 메모리 카운터는
  인스턴스마다 따로 세어 소용이 없어서 DB에서 `INSERT ... ON CONFLICT` 로 원자적으로
  올린다 — 읽고 나서 쓰면 동시 요청이 한도를 넘긴다(동시 30건 테스트로 확인).
  IP는 그대로 저장하지 않는다. 필요한 건 "같은 곳에서 몇 번 왔나"뿐이다.

여기서도 같은 함정을 한 번 더 밟았다. LQ 기준선을 자리마다
`count(*) FILTER (...) / count(*) FROM place` 로 구해 691,087행을 두 번 훑었다(자리당 977ms).
`analyzeDongs` 에서 이미 고쳤던 실수다. 기준선은 업종에만 달린 값이라 한 번만 구하면 되고,
분모를 `dong_stat` 합계로 바꾸면 22ms다. 쿼리도 순차로 던져 왕복 지연이 8번 쌓이고 있었다.
**10.8초 → 0.5초.**

## 화면

카카오 기본 지도는 밝고 라벨이 빽빽하다. 그 위에 데이터를 얹으면 대부분 묻힌다. 그래서:

- **반경 원을 두 겹으로 그린다** — 굵은 흰 선을 깔고 그 위에 자주색 실선. 배경이 무엇이든 경계가 선다
- **클러스터를 카카오 기본(형광 연두·노랑)에서 바꿨다** — 배경 지도의 노란 도로와 섞여 읽히지 않았다. 어두운 판에 흰 숫자로
- **내가 찍은 자리는 크로스헤어**다. 동그라미로 두면 클러스터 마커와 형태가 같아서 색만으로는 구분되지 않는다
- **업종은 소분류(편의점·미용실·카페)로 보여준다.** 처음엔 대분류(소매·음식)로 만들었는데, "소매 994곳"은 창업자가 판단에 쓸 수 없는 숫자다. 원본에 246개 소분류가 이미 있어서, 사람이 아는 이름 그대로 셀 수 있다
- **업종 선택은 두 단계가 맞물린다.** 위 select는 대분류, 아래 목록은 소분류다. 소분류를 고르면 select에는 그 상위 대분류가 표시되고, 목록은 그 안에서 다시 나뉜다(음식 → 백반/한정식 171, 카페 112, 요리 주점 106). 형제 업종을 계속 보여주는 이유는 고른 것만 남으면 비교가 안 되기 때문이다. 코드가 접두어 구조라 파라미터 하나로 두 단계를 다 처리한다
- **업종 분포는 막대가 아니라 행 자체가 채워진다.** 색은 순위가 아니라 최대 업종 대비 비율로 정한다 — 순위로 칠하면 2위가 1위의 90%든 5%든 같은 색이라 색이 아무것도 말해주지 않는다
- 계측값(개수·거리·반경·업종 코드)은 전부 mono로 셋팅한다. 자릿수가 흔들리면 값을 비교할 수 없다
- **장소 검색**을 넣었다(카카오맵 `services` 라이브러리, 지도용 JS 키를 그대로 쓴다). 내 위치만
  쓰면 인천에 있지 않은 사람은 부평역만 보게 된다. 자기가 아는 동네를 찍어봐야 서비스가 와닿는다.
  커버리지 밖 결과도 지도는 옮기되 0곳이 나오는 이유를 함께 알린다 — 결과에서 빼버리면
  "왜 안 나오지"가 된다
- **모바일은 3단 서랍**이다(요약 / 절반 / 전체). 끌면 따라오고 놓으면 가까운 단계로 붙는다.
  필터도 접어서 내용이 들어갈 자리를 넓혔다. 서랍 높이가 바뀌면 지도를 밀어 올려 고른 자리가
  가려지지 않게 한다 — 자리를 고르는 도구인데 고른 자리가 안 보이면 안 된다
- **업소를 누르면 서랍이 올라오며 상세를 보여준다.** 요약(63px)에 접혀 있을 때 마커를 누르면
  상세만 바뀌고 화면은 그대로여서, 눌렀는데 아무 일도 안 일어난 것처럼 보였다. 닫으면 원래
  높이로 돌아간다. 상세를 보는 중에는 검색·필터·탭을 감춘다 — 업소 하나를 들여다보는데 그것들이
  자리를 차지하면 정작 정보가 화면 밖으로 밀린다
- **지도 앱 관습을 따랐다.** 지도를 옮겨도 분석이 이전 자리에 머물러 있었고, 현재위치 버튼은
  패널 안에 묻혀 있었고, 줌 버튼은 아예 없어 모바일에서는 핀치만 가능했다.
  `이 지역에서 다시 찾기` 버튼과 지도 위 플로팅 컨트롤(현재위치·확대·축소)을 올렸다.
  **자동으로 다시 계산하지는 않는다** — 손가락을 뗄 때마다 조회가 나가고 사용자가 고른 자리도
  제멋대로 바뀐다. 반경의 40%를 넘게 벗어났을 때만 버튼을 띄운다(조금 흔들린 정도로 뜨면 성가시다)
- **검색은 타이핑이 멈추면 알아서 찾는다.** 글자마다 부르면 카카오 Local API 쿼터를 빠르게 쓰므로
  300ms 디바운스에 두 글자 이상일 때만 호출한다
- **마커 터치 타깃은 40px**다. 보이는 점은 20px 그대로고 투명 여백만 둘렀다. 마우스로는 충분한
  크기가 손가락으로는 빗나간다

**접근성** — 측정해보니 `aria-live` 영역이 0개였다. 반경이나 업종을 바꾸면 화면의 숫자는
바뀌는데, 시각적으로 보지 않으면 아무 일도 일어나지 않은 것과 같았다. 이 서비스의 답이 바로
그 숫자다. sr-only 라이브 영역에 `반경 500m 안 카페 112곳` 한 줄을 넣고, 조회 중에는 비운다 —
중간 상태를 읽어주면 소음이 된다. 검색 결과는 combobox/listbox 패턴으로 바꿔 방향키·Enter·
Escape로 조작한다(이전에는 마우스로만 고를 수 있었다).

색은 **지적편집도**에서 가져왔다. 지적도에서 상업지역은 분홍으로 칠하는데, 이 서비스가 다루는 땅이 정확히 거기다.

### 데이터 적재

원본 데이터(1.5GB)는 저장소에 포함하지 않는다.
[공공데이터포털](https://www.data.go.kr/data/15083033/fileData.do)에서 ZIP을 받는다. ZIP은 **시도별 16개 CSV**로 나뉘어 있고, 인천만 쓴다.

ZIP 내부 파일명이 CP949로 저장돼 있어 `unzip`으로 풀면 이름이 깨진다:

```bash
python3 -c "
import zipfile, pathlib
z = zipfile.ZipFile('<받은파일>.zip', metadata_encoding='cp949')
dst = pathlib.Path('data')
for n in z.namelist():
    if '인천' in n:
        (dst / pathlib.Path(n).name).write_bytes(z.read(n))
        print(pathlib.Path(n).name)
"
```

그다음:

```bash
pnpm data:inspect "data/소상공인시장진흥공단_상가(상권)정보_인천_202606.csv"   # 실사 먼저
pnpm db:migrate
docker exec -i jario-db psql -U jario -d jario -c "TRUNCATE staging_place; \
  COPY staging_place FROM '/data/소상공인시장진흥공단_상가(상권)정보_인천_202606.csv' \
  WITH (FORMAT csv, HEADER true, ENCODING 'UTF8');"
pnpm data:transform                                                          # staging → place/industry
pnpm db:check                                                                # 좌표계·인덱스 검증
pnpm test                                                                    # 58건
```

## 테스트

```bash
pnpm test
```

목(mock)을 쓰지 않는다. 이 프로젝트에서 틀릴 수 있는 건 TypeScript가 아니라 SQL이다 —
geography 거리 계산, 업종 접두어 매칭, 표본 추출이 전부 DB 안에서 일어난다.
그래서 통합 테스트는 로컬 PostGIS의 실제 인천 데이터를 그대로 쓴다(적재가 선행돼야 한다).

테스트가 실제로 회귀를 잡는지도 확인했다. `geography`를 `geometry`로 바꿔
거리 단위를 도(degree)로 되돌리자 **8건이 실패**했다.

### OG 이미지는 유닛 테스트로 못 잡는다

`node --test` 는 JSX를 읽지 못하고, 무엇보다 **Satori의 실패는 빈 응답으로 나온다** —
빌드는 통과하고 페이지도 멀쩡한데 미리보기만 죽는다. 실제로 한 번 겪었다
(`Expected <div> to have explicit display: flex` → `failed to pipe response`).

그래서 `scripts/smoke.sh` 가 빌드된 앱을 띄워 HTTP로 훑는다. 200인지가 아니라
**PNG 매직 바이트와 크기**를 본다. `display:flex` 를 다시 빼서 회귀를 주입해,
`FAIL 리포트 OG 이미지 — PNG가 아니거나 너무 작다 (0B)` 로 잡히는 것까지 확인했다.

처음엔 이 스크립트가 조용히 죽었다. `set -e` 가 curl 실패(빈 응답)에서 먼저 스크립트를
끝내버려서 종료코드 52만 남았다 — 검증 도구가 무엇이 실패했는지 못 말하면 소용이 없다.

### CI에서 DB가 필요한 테스트를 어떻게 돌리나

원본 CSV(72MB)는 저장소에 없다. 목으로 바꾸면 정작 검증하려는 SQL이 사라진다.
그래서 **행정동 11개를 온전히 담은 시드 픽스처**(`tests/fixtures/seed.csv.gz`, 2.6MB)를
커밋하고, CI가 같은 ETL을 그대로 돌린다 — 마이그레이션 → `COPY` → `transform.sql` →
`refresh-stats.sql` → 좌표계 검증 → lint → test → build.

부평역 500m = 3,074, 강남역 500m = 6,615 같은 실제 검증값이 픽스처에서도 그대로 나온다.

픽스처 설계에서 두 번 갈아엎었다.

- 처음엔 **반경으로 잘랐더니** 행정동이 중간에 잘렸다. 동의 평균 좌표가 인위적으로
  밀집지 쪽으로 당겨져서, 대표 지점 로직("동 전체가 담겨 있다"는 전제)이 깨졌다.
- 행정동 단위로 온전히 담아도 한 테스트는 여전히 실패했다. **두 지점의 반경 500m 이웃**을
  비교하는데 그 이웃이 픽스처 경계 밖으로 뻗으면서 두 지점이 서로 다르게 잘린다.
  부분 데이터로는 성립할 수 없는 검증이라, 전체 데이터에서만 돌도록 표시했다.

그래서 CI는 **57 pass + 1 skip**, 로컬 전체 데이터는 **58 pass**다. 건너뛴 이유는
테스트 코드에 남겼다.

적재는 애플리케이션 INSERT가 아니라 서버측 `COPY`다 (13만 행 0.8초). `data/`는 컨테이너에 `/data`로 마운트돼 있다.

스키마를 추측하지 않고 항상 `data:inspect`를 먼저 돌린다.
공공데이터는 분기마다 컬럼이 조용히 바뀌고, 동봉 문서가 실제 데이터와 다른 경우도 있다(실제로 그랬다).


psql을 로컬에 설치하지 않고 `jario-db` 컨테이너 안의 psql을 쓴다. CSV가 이미 `/data`로

되돌리기 어려운 작업이라 대상 호스트를 보여주고 확인을 받는다.

### 어느 연결을 쓰는가

Supabase는 세 가지 접속 경로를 주는데 셋 다 성격이 다르다.

| 경로 | 포트 | 여기서의 용도 |
|---|---|---|
| 직접 연결 `db.<ref>.supabase.co` | 5432 | **못 씀** |
| 세션 모드 풀러 | 5432 | 마이그레이션·`COPY` |
| 트랜잭션 모드 풀러 | 6543 | 앱(Vercel) |

**직접 연결은 IPv4 주소가 없다.** `db.<ref>.supabase.co`에는 AAAA 레코드만 있고 A 레코드가
없다(IPv4는 유료 부가기능). IPv6가 나가는 환경이었는데도 Node의 `dns.lookup`(getaddrinfo)이
`ENOTFOUND`로 실패했다 — `dns.resolve6`으로는 주소가 나온다. 그래서 관리 작업도 풀러를 쓴다.

프로젝트가 `aws-0`인지 `aws-1`인지는 DNS로 알 수 없다(둘 다 존재한다). 실제로 붙어보면
아닌 쪽은 `tenant/user ... not found`로 거절한다.

### 서버리스에서 조심한 것

- **트랜잭션 모드 풀러로 붙을 때 `prepare: false`.** prepared statement가 세션을 넘어
  살아남지 못해 `prepared statement ... already exists`가 산발적으로 난다.
  로컬에서는 재현되지 않고 배포 후 트래픽이 붙어야 나타난다. 연결 문자열을 보고 자동 판별한다.
- **인스턴스당 커넥션 `max: 1`.** 인스턴스 수만큼 곱해진다.
- **`transform.sql`은 staging이 비어 있으면 실패한다.** 이 가드가 없으면 `place`를 통째로
  비운 뒤 0건을 넣고 "성공"으로 끝난다. 무료 티어 용량을 아끼려고 staging을 비워두기 때문에
  실제로 밟기 쉬운 함정이다(적재 후 staging 71MB를 비워 DB를 169MB → 99MB로 줄였다).

### 무료 티어 500MB에 서울·인천을 넣기

전국 데이터를 한 번에 올리면 들어가지 않는다. **최종 크기가 아니라 적재 중 최대치가 문제**다 —
`staging`과 `place`가 동시에 존재하는 순간이 정점이고, 서울·인천을 한 번에 올리면
staging 354MB + place 323MB = 677MB가 된다.

두 가지로 해결했다.

- **안 쓰는 인덱스를 지웠다.** `place_name_trgm_idx`가 53MB를 쓰면서 스캔 횟수가 0이었다.
  "나중에 상호명 검색에 쓸 것"이라며 만들어놓고 구현한 적이 없는 인덱스였다.
  인천만 있을 때는 눈에 안 띄다가 서울을 더하니 place의 14%였다.
- **지역을 청크로 나눠 덧붙인다**(`scripts/push-region.sh`). 20만 행씩 끊어
  staging을 비우며 넣으면 정점이 426MB로 내려간다. `append.sql`은 멱등이라
  (`ON CONFLICT DO NOTHING`) 중간에 끊겨도 그 청크만 다시 돌리면 된다.
  실제로 3번째 청크에서 연결이 끊겼고 그렇게 복구했다.

### 링크를 살려두기

Supabase 무료 티어는 **일주일 요청이 없으면 프로젝트를 일시정지**한다. 포트폴리오는 링크가
살아 있는 것이 전부라, 죽은 링크는 없는 것보다 나쁘다.

`.github/workflows/keepalive.yml`이 3일마다 배포된 API를 호출한다. 단순 핑이 아니라
응답의 `total`이 1,000 이상인지까지 본다 — DB가 멈췄거나 연결이 끊기면 200이 떠도
`total`이 0이 되기 때문이다. 유지 장치이자 최소한의 감시다.

⚠️ GitHub Actions의 `schedule`은 **저장소가 60일간 활동이 없으면 자동으로 비활성화**된다.
장기간 손대지 않을 거라면 외부 모니터링(UptimeRobot 등)을 함께 두는 편이 안전하다.

### 배포 후 할 것

카카오 콘솔 `[앱 → 플랫폼 키 → JavaScript 키 → JavaScript SDK 도메인]`에 배포 도메인을 추가한다.
JS 키는 브라우저에 노출되므로 도메인 제한이 유일한 방어다. 운영에 올린 뒤에는
`http://localhost:3001`을 빼는 편이 안전하다.

## 응답 68초를 0.2초로

서울을 더해 691,087행이 되자 `/api/analysis/dong` 이 **68초**가 됐다. 로컬에서는 0.57초라
전혀 보이지 않았고, Supabase 무료 티어의 느린 공유 I/O에서만 드러나는 종류였다.
원인이 네 겹이었고 실행계획을 나눠 보며 하나씩 걷어냈다.

| # | 원인 | 근거 | 조치 |
|---|---|---|---|
| 1 | 업종 접두어가 인덱스를 못 탐 | `Parallel Seq Scan on place 5,603ms` | `text_pattern_ops` 인덱스 (0005) |
| 2 | 인덱스는 타지만 힙 접근이 남음 | `Bitmap Heap Scan 2,103ms`, `Heap Blocks 17,724` | 행정동·좌표를 `INCLUDE` 한 커버링 인덱스 (0006) → `Heap Fetches: 0`, 161ms |
| 3 | 동별 총계를 매번 전체 집계 | 691,087행 full scan, 인덱스로 제거 불가 | 585행 `dong_stat` 으로 사전 계산 (0007) |
| 4 | 함수가 미국에서 실행 | `x-vercel-id: icn1::iad1` | `regions: ["icn1"]` |

1번이 특히 뼈아프다. `industry_code LIKE 'I2%'` 는 대/중/소를 파라미터 하나로 처리하는
이 서비스 설계의 핵심인데, 기본 btree는 C가 아닌 collation에서 접두어 검색에 쓰이지 않는다.
정작 핵심 경로에 인덱스가 없었다.

4번은 DB 쿼리가 289ms인데 응답이 1.9초였던 이유다. 요청은 서울 엣지로 들어오지만
함수는 워싱턴에서 돌고, 거기서 서울 DB로 태평양을 왕복하고 있었다.

커넥션 `max: 1` 도 문제였다. 목록·집계를 `Promise.all` 로 병렬 호출해도 한 줄로 서서
응답 시간이 그대로 두 배가 된다.

```
/api/analysis/dong   68s   → 0.18~0.22s
/api/places/nearby   5.7s  → 0.38~0.65s
```

## 화면이 뜨기까지 1.75초 → 0.25초

FCP가 1,752ms였다. 원인의 대부분이 **한글 폰트**였다.

`next/font`는 기본으로 모든 폰트 페이스를 `<link rel=preload>` 로 건다. 한글은 유니코드
서브셋이 100개 남짓으로 쪼개지고, 굵기까지 곱하면 **페이스가 393개**가 된다. 그걸 전부
미리 받고 있었다 — 폰트 파일 246개 · 2,143KB · preload 링크 283개. 화면에 실제로 쓰는
글자는 수백 자뿐인데. 라틴 전용 프로젝트에서는 합리적인 기본값이 한글에서는 정반대로 작동한다.

`preload: false` 로 두면 브라우저가 실제 쓰인 글자의 서브셋만 가져온다. 덤으로 `font-bold`(700)를
코드에서 한 번도 쓰지 않으면서 굵기 하나를 통째로 받고 있었다.

나머지 둘:

- **페이지에서 DB를 없앴다.** 업종 목록 10행을 읽느라 `force-dynamic` 이었다.
  어차피 한 번은 나가는 조회 응답에 얹으니 `○ (Static)` 이 됐다. TTFB 147ms → 70ms
- **화면 하나가 조회를 세 번 보냈다.** `/api/spot` 으로 합쳤다. 병렬이라 벽시계 시간은
  최댓값이었지만 서버리스 호출 3번 = 콜드 스타트 확률 3배였다.

| | 전 | 후 |
|---|---:|---:|
| FCP | 1,752ms | 248ms |
| TTFB | 147ms | 70ms |
| 전송량 | 2,217KB | 425KB |
| 요청 수 / 화면 | 3 | 1 |

### 합치면서 만든 버그 셋

통합은 공짜가 아니었다. 한 요청에 쿼리를 5개 몰아넣자 새 문제가 생겼다.

- **`Promise.all` 이 프로세스를 죽였다.** 하나가 거부되면 즉시 실패하지만 나머지 프로미스는
  나중에 각자 거부된다. 핸들러가 없으면 `unhandledRejection` → `exit 128`. 사용자가 반경을
  빠르게 바꾸면 이전 요청이 중단되고 DB 쿼리가 취소되므로 흔히 발생한다. 프로세스가 죽은 뒤
  요청들이 500/504를 맞았다. 각 프로미스에 미리 핸들러를 붙여 막는다.
- **커넥션이 모자랐다.** `max: 3` 인데 쿼리가 5개. 남는 커넥션을 기다리다 함수 타임아웃까지
  갔다. 측정으로 좁혔다 — 쿼리 2개짜리 `/api/places/nearby` 는 6/6 성공, 쿼리 5개짜리
  `/api/spot` 은 성공/504가 정확히 교대했다.
- **패널이 통째로 비었다.** TanStack Query v5는 `queryKey` 가 바뀌면 새 데이터가 올 때까지
  `data` 가 `undefined` 다. 업종 목록을 서버 prop에서 응답으로 옮기면서, 반경을 바꿀 때마다
  select 옵션까지 사라졌다 돌아왔다. `placeholderData: keepPreviousData` 로 막는다.

넣지 않은 것과 그 이유:

- **인증·내 리포트 목록** — 링크 공유만으로 목적이 달성되고, 로그인은 데모의 마찰만 늘린다.
- **격자 히트맵** — 지도 전체를 칠하려면 폴리곤 수천 개가 필요해 카카오맵 오버레이로는
  감당이 안 된다. MapLibre + 벡터타일 전환과 함께 다뤄야 한다.
- **상호명 검색 인덱스** — 만들어놓고 쓰지 않아 53MB를 낭비하고 있었다. 지웠다.
  실제로 검색을 만들 때 다시 넣는다.

아직 못 한 것:

- **경기도 추가** — DB가 370MB/500MB라 무료 티어로는 더 들어가지 않는다.
